# Plan — one arXiv id parser (2026-10-31)

Ticket #66 (T1 of spec #65). Evidence: four accept sets for one identifier — the fetcher's URL
fragment, the metadata helper's validator, the licence pass's response matcher (modern-only, which
is why `gnr` has no licence record), and the year query's own tail parse.

## What

- `scripts/entry.py`: `ARXIV_ID` (the shared fragment), `ArxivId` (id, lowercase key, revision,
  year), `parse()`, typed `IdError`. Case is preserved in `id` so stored bytes do not move;
  `key` is lowercase for lookups.
- Fetcher: the URL fragments use the shared one; `normalise_arxiv_id` delegates.
- Metadata helper: validation, canonical key and revision come from `parse()`.
- Licence pass: response ids are parsed with the same rule, so a legacy id is no longer skipped;
  the response parser is extracted so it can be exercised with a fixture.
- Year query: `parse().year`.

## Why

One accept set is the difference between "the corpus knows this id" and "this consumer knows this
id". The legacy row is the proof: accepted by the index, rejected by the licence pass.

## Verification

- fixtures: modern, version-suffixed, legacy, subclass, malformed (rejected by name)
- every id in the manifest parses; `gnr` is among them
- a fixture Atom response containing a legacy id yields a record
- `--index` byte-identical; gate 3/3

## Out of scope

Statuses (T2), consumer vocabulary deletion and gate invariants (T3).
